# UI 컴포넌트 시스템 대안 비교 — DaisyUI vs shadcn/ui vs 현상 체계화

> 작성: 2026-05-24 · 상태: **결정 전(비교용)** · 트리거: "컴포넌트를 DaisyUI로 전부 교체하면 공수가?"

## 1. 진짜 목표 (사용자 확인)

1. **일관성** — 뷰마다 디자인이 제각각으로 느껴진다.
2. **테마/다크모드** — 룩을 바꾸거나 다크모드를 넣고 싶다.

→ 핵심: 목표는 "DaisyUI 도입"이 아니라 **일관성 + 토큰 기반 테마**다. 라이브러리는 수단일 뿐.

## 2. 현재 상태 (실측, 2026-05-24)

| 항목                | 수치                                                            | 함의                             |
| ------------------- | --------------------------------------------------------------- | -------------------------------- |
| `.tsx`              | 40개 / ~10,012줄                                                | 7개 대형 뷰 + 30여 컴포넌트      |
| `styles.css`        | 6,057줄 / ~211 셀렉터 / ~25 네임스페이스                        | 뷰별 손작성 CSS                  |
| 컬러 토큰(`@theme`) | 28개 + radius/폰트 토큰                                         | **토큰 레이어 이미 존재**        |
| 컬러 사용           | `var(--color-*)` **915회** vs 하드코딩 ~99회(hex 65 + rgb 34)   | **~90% 토큰화 (양호)**           |
| 다크모드            | 없음(`color-scheme: light` 1줄, 토글 없음)                      | 그러나 토큰 구조라 추가는 국소적 |
| UI 라이브러리       | **없음** (daisy·shadcn·radix·cva 미설치)                        | cmdk·lucide·clsx/tw-merge만      |
| 직접 프리미티브     | `<button>` 173 · `<input>` 34 · `<select>` 14 · `<textarea>` 12 | 공용 컴포넌트 없이 인라인 반복   |

**두 가지 핵심 진단:**

- **(A) 다크모드/테마의 비싼 부분(토큰화)은 이미 ~90% 완료.** 남은 일은 "28토큰 다크값 + 하드코딩 ~99개 정리 + 토글". 라이브러리와 무관하게 가능하고, DaisyUI는 오히려 이 자산(915 참조)을 버리게 만든다.
- **(B) 일관성 부재의 원인은 토큰 부재가 아니라 공용 프리미티브 부재.** 25개 네임스페이스가 버튼·카드·뱃지를 각자 재구현 → 미세 드리프트. 해법은 "Button/Input/Card/Badge/Modal 등 공용 프리미티브 추출".

## 3. 평가 기준

목표 적합도(일관성·다크모드) · 디자인 제어(DESIGN.md Cohere 정합) · 공수 · 리스크 · 기존 자산 재사용 · 거버넌스(AGENTS.md "shadcn 위에") · 점진 도입 가능.

## 4. 대안

### A. DaisyUI 전면 교체

- **방식:** Tailwind v4 `@plugin "daisyui"` + 커스텀 테마, className을 daisy 클래스(`btn`/`card`/`modal`…)로 재작성, 6k CSS 대거 철거.
- 일관성 ✅ / 다크모드 ✅(`data-theme` 내장)
- **단점:** 기존 28토큰/915참조 체계를 daisy 자체 시맨틱 토큰(primary/base-100…)으로 **갈아엎음**. DESIGN.md(절제된 화이트 에디토리얼) ↔ daisy 특유 룩 충돌 → 결국 커스텀 테마로 눌러야 해 daisy 장점 상쇄. bespoke 뷰(매트릭스·diff·에이전트바·캘린더 = 시각 표면 ~40–50%)는 이득 거의 없음. AGENTS.md 위배.
- **공수: ~3–5주(15–25일). 리스크 높음**(자동 비주얼 테스트 0, 디자인 드리프트, 결정 레일/IPC 회귀 위험).

### B. shadcn/ui (working agreement가 지정한 길, 점진)

- **방식:** 필요한 프리미티브만 복사해 **코드를 소유**하고 DESIGN.md 토큰으로 restyle. 뷰 단위 점진 채택.
- 일관성 ✅ / 다크모드 ✅ — **shadcn 표준 패턴 = CSS 변수 토큰 + `.dark` 클래스**라 기존 `--color-wr-*`에 그대로 매핑(915참조 재사용). 다크모드 아키텍처가 공짜로 정렬됨.
- 디자인 제어 ✅(컴포넌트 코드 소유) · Tailwind v4 + 기존 토큰 정합 · AGENTS.md 충족.
- **단점:** 프리미티브 추출/restyle 초기 비용. bespoke 뷰는 여전히 커스텀(단, 내부 버튼/입력은 공용화).
- **공수: 프리미티브 추출 + 다크모드 기반 ~1–1.5주, 전뷰 점진 채택 +2–3주(분할 가능). 리스크 낮음, 버리는 자산 없음.**

### C. 현상 유지 + 체계화 (라이브러리 미도입)

- **방식:** 기존 클래스 위에 자체 `<Button>/<Input>/<Card>` 래퍼 추출 + 하드코딩 컬러 금지 lint + 다크 토큰 추가.
- 일관성 ✅(자체 프리미티브) / 다크모드 ✅ — **가장 저렴**(다크 토큰값 + 하드코딩 ~99개 + 토글 = ~3–4일).
- 디자인 제어 ✅✅(완전 자체) · 새 의존성 0 · 완전 온브랜드.
- **단점:** 커뮤니티 컴포넌트 없음(모든 프리미티브 자작), **신규 UI 개발 속도 이득은 가장 작음**.
- **공수: 다크모드 ~3–4일 + 일관성(프리미티브 8–10개 추출·마이그레이션) ~1.5–2.5주.**

## 5. 비교표

| 기준                | A. DaisyUI              | B. shadcn/ui        | C. 자체 체계화          |
| ------------------- | ----------------------- | ------------------- | ----------------------- |
| 일관성              | ◎                       | ◎                   | ○ (자작 필요)           |
| 다크모드/테마       | ◎(내장, 단 토큰 재구축) | ◎(기존 토큰 재사용) | ◎(가장 저렴)            |
| DESIGN.md 정합      | △(룩 충돌)              | ◎                   | ◎                       |
| 기존 자산 재사용    | ✕(915참조 폐기)         | ◎                   | ◎                       |
| 거버넌스(AGENTS.md) | ✕ 위배                  | ◎ 부합              | △(정책 갱신 필요)       |

| 리스크              | 높음                    | 낮음                | 낮음                    |

## 6. 권고

1. **다크모드/테마는 라이브러리 결정과 분리해 지금 바로(B/C 공통 기반).** 기존 28토큰에 다크값 정의 + 하드코딩 ~99개 토큰화 + `data-theme`(또는 `.dark`) 토글. ~3–4일, 가치 높음, 어느 길로 가든 버려지지 않음. **DaisyUI는 이 목적에 최악**(토큰 체계 폐기).
2. **일관성은 공용 프리미티브 추출 문제 → shadcn/ui(B) 권장.** 이미 지정된 길이고, 기존 토큰 위에 얹혀 다크모드 패턴까지 정렬되며, 코드 소유로 Cohere 룩 유지 + 점진 도입 가능. "새 의존성 0"이 강한 제약이면 C도 유효.
3. **DaisyUI(A)는 비추.** 목표(일관성·테마) 대비 비용·리스크·룩 충돌·자산 폐기가 가장 크고, AGENTS.md/DESIGN.md 갱신까지 강제.

## 7. 다음 단계 제안

- (선택) **PoC 1뷰**: `SettingsView`(폼·카드·토글 밀집)를 shadcn 프리미티브 + 다크 토큰으로 변환해 룩·공수를 실측.
- (병행 가능) **다크모드 기반 PR**: 토큰 다크값 + 하드코딩 정리 + 토글(결정 레일/IPC 무관, 작은 PR).
- 결정 후 `AGENTS.md`/`DESIGN.md` 컴포넌트 정책 한 줄 갱신 + `docs/decisions.md` 기록.

## 8. 미해결/가정

- 공수는 단독 개발 + 수동 QA 기준(자동 비주얼 테스트 없음). 분할 PR로 리스크 완화 가능.
- bespoke 뷰(MatrixCanvas·WorktreeView diff·AgentStatusBar·Calendar·SprintTimer)는 **어느 안에서도 레이아웃은 커스텀 유지** — 라이브러리 이득은 그 내부 프리미티브에 한정.

## 9. PoC 결과 (2026-05-24, 동일 슬라이스 비교)

`poc.html`(격리 vite 엔트리, mock 데이터, 앱 무수정)로 동일 "프로젝트 설정 카드"를 양쪽 구현 + 다크 토글.

**코드량:** DaisyUI = 컴포넌트 파일 0 + 데모 91줄 + dep 1(daisyui). shadcn = 소유 프리미티브 8파일/282줄 + 데모 112줄 + dep 4(cva + radix×3).

**라이트:** 동점. 같은 Cohere 토큰을 먹이면 daisy도 shadcn만큼 에디토리얼 톤에 맞음. daisy가 코드 더 적음.

**다크(결정적):** shadcn = 전부 정상(`.dark`+CSS변수 = 레포 기존 915참조 모델과 동일, 다크값만 추가하면 떨어짐). DaisyUI = **토글 2개 실종 + 인풋 대비 소실 + 뱃지 저대비** — daisy는 컴포넌트 내부 변수 체계가 깊어 base 팔레트 수동 매핑만으로 패리티 미달. 동일 공수에서 shadcn이 다크 패리티 도달, daisy는 추가 테마 튜닝 필요.

**결론 보강:** "daisy가 어렵다"의 정체 = 컴포넌트 사용이 아니라 (1) 기존 토큰 체계 정합 + (2) 다크 충실도. 둘 다 사용자 목표라 daisy가 그 지점에서 비쌈. daisy 다크 버그는 튜닝으로 해결 가능(불가 아님). 권고는 §6 유지: **shadcn 점진 + 다크모드 선반영**. daisy 채택 시 "라이트+다크 테마 정밀 튜닝" 공수를 별도 계상할 것.
