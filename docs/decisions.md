## Phase 3 — Notion 승격 (write 레일) (2026-05-21)

- **승격 흐름 = 즉시 write(사용자 결정).** 카드 메뉴 "백로그 등록/안건 승격"을 누르면 draft→accept 2단계 없이 곧바로 Notion API write한다. **INVARIANT #2 해석:** Acceptance 게이트는 *자동화(Codex) 출력*이 외부를 직접 mutate하지 못하게 막는 장치다(architecture §2 제안/실행 레일). 사람이 직접 카드 메뉴를 누르는 것은 *그 자체가 사람의 결정/accept*이므로(Phase 1의 "Today 추가"가 로컬 즉시 액션이었던 것과 동일 논리) 별도 확인 단계가 필요 없다. Phase 3 경로엔 자동화가 없다(자동 draft는 Phase 9). `acceptances` 테이블은 `agent_run_id` FK 전용이라 이 경로에 미관여. **단, `Promotion.status='confirmed'` 경로는 Phase 9 자동화-draft의 2단계 게이트(draft→사람 confirm→write)를 위해 보존**한다(이번 단계 미사용). 즉시 write여도 `promotions`에 draft→created 전이를 남겨 undo/audit 데이터를 확보한다.
- **신규 마이그레이션 없음.** `promotions`(0001)에 status(draft/confirmed/created/failed)·created_external_id·draft_payload(JSON)가 이미 있어 재사용. **오프라인 큐 = `promotions`의 draft 행 재사용**(별도 큐 테이블 없음): write 실패가 일시적(네트워크/429/5xx)이면 draft로 남고(=큐잉), 복구 시 `flush_promotions`가 draft→created 전이. 영구 실패(4xx)는 `failed`로 표시(자동 flush 대상 아님). `confirmed`는 자동화용 예약.
- **Notion 페이지 매핑 = title 속성만 필수.** `GET /v1/databases/{id}`로 title 타입 속성명을 발견(이름/언어 무관, `type=='title'` 기준)해 그 속성만 채운다(스키마 가정 최소화, 나머지 선택). 발견 결과는 db_id별 캐시(flush 시 반복 read로 rate limit 낭비 방지).
- **rate-limit 인지 + bounded retry(INVARIANT #5).** `notion.rs`: `RateLimiter`로 요청 간 최소 간격(~3 req/s) pacing + `with_retry`(시도 캡 3 + 지수 backoff + jitter). **Terminal(4xx, 429 제외)은 재시도하지 않고**, Transient(네트워크/429/5xx)만 backoff 후 재시도하며 소진 시 terminal failure를 노출한다(무한 retry/poll 금지). 분류·재시도·title 발견은 fake writer/순수 로직으로 cargo test 검증(실 네트워크 없음 — 헤드리스 CI 가능).
- **멱등(INVARIANT #3).** 같은 (signal,target)이 이미 `created`면 재클릭이 중복 write/행 없이 기존 outcome(+pageUrl)을 반환하고, 오프라인 재클릭은 같은 draft 행을 재사용한다(큐 중복 0).
- **"Notion에서 열기" = tauri-plugin-opener.** 성공 시 생성된 페이지 URL을 `openUrl`로 외부(브라우저/Notion 앱)에서 연다(토큰과 무관). capability에 `opener:allow-open-url` 추가. 토큰은 `promote_to_notion` 인자에 없고 keychain에서만 읽혀 Rust 안에서만 쓰인다(렌더러 미노출 유지).
- **테스트 가능 seam.** 외부 write는 `NotionWriter` 트레잇(RPITIT, async_trait 무의존)으로 추상화 → 승격 코어 `execute_promotion`은 fake writer로 lifecycle(created/큐잉/failed/멱등/flush 전이) 검증. 실 Notion write·페이지 오픈·실제 오프라인 동작은 헤드리스 불가 → 사용자 관찰 항목(Phase 1/2 GUI 항목과 동일).
- **동시 승격 직렬화(INVARIANT #3, reviewer 지적 B1 보강).** 멱등 체크는 check-then-act라 더블클릭/`flush vs 수동` 경합 시 둘 다 created 없음을 보고 write를 2번 호출해 **중복 Notion 페이지**가 생길 수 있었다. → (1) `execute_promotion`을 in-process `PROMOTION_GATE`(tokio Mutex)로 직렬화(단일 프로세스 백엔드 → 충분; 네트워크는 이미 RateLimiter paced) + (2) **마이그레이션 0003**: `promotions(signal_id,target) WHERE status='created'` partial unique index로 DB 레벨 구조적 2차 방어선("structural enforcement over prose", ADR-0013 차용). 동시성 테스트(`concurrent_promote_writes_once`: write 1회·created 1행) + 인덱스 테스트 추가. 부수로 `flush_inner`는 한 건 DB 오류가 배치를 멈추지 않게 per-item으로 격리(reviewer nit N1). per-(signal,target) 게이트 분리는 단일 사용자엔 불필요 → 향후 최적화.

## Phase 4 — GitHub PR Radar (read 레일) (2026-05-21)

- **Escalate 임계치 = CI 실패 + 링크 백로그 티켓(사용자 결정).** PR이 매트릭스로 올라오는 조건은 `state=open && CI=failing && (ticketKeyPattern로 PR title/branch에서 추출한 링크 티켓 존재)` 단 하나. INVARIANT #4(매트릭스=결정 큐, 거울 아님) 준수 — 나머지 PR은 PR Radar 자기 뷰(버킷)에만 산다. done-criteria의 "오늘 마감 백로그 링크"에서 *마감일*은 Notion 백로그 내용 미러가 없는 Phase 4에선 도출 불가 → 마감일 기반 정교화는 Notion 미러가 생기는 Phase 6로 연기하고, Phase 4는 GitHub만으로 도출 가능한 "링크 티켓 존재"로 임계치를 정의한다.
- **escalate 진입 = unclassified + suggestedQuadrant 힌트(사용자 결정, INVARIANT #1 엄수).** done-criteria #2는 "Q1에 1건"이라 적혔지만 INVARIANT #1("카드는 항상 unclassified 진입, 자동 분류 금지, suggested는 힌트")이 최우선. → PR 신호는 `quadrant=unclassified`로 진입하고 `suggested_quadrant='q1_do_now'`를 힌트로만 단다. "Q1에 1건"은 "Q1 제안(힌트) 1건 / 미분류 1건"으로 해석해 검증. 실제 사분면 배치는 사람이 드래그/키보드로만(classify_signal). INVARIANT 충돌 시 INVARIANT가 done-criteria 문구를 이긴다.
- **dedup 키 = `pr:{owner}/{repo}:{number}:{reason}`(사용자 결정, INVARIANT #3).** repo full-name 포함으로 멀티레포 PR번호 충돌 방지(architecture 예시 `pr:42:ci_failed`를 멀티레포 안전형으로 확장). reason는 escalate 사유(`ci_failed`). 폴링 N회 → 기존 `idx_signals_dedup`(0001 partial unique) 위 `ON CONFLICT(dedup_key) DO UPDATE`로 1행 유지(중복 0). **conflict 시 quadrant/status는 건드리지 않는다**(사람 결정 보존 — INVARIANT #1); title/body/links/suggested_quadrant/updated_at만 갱신.
- **auto-resolve = 원인 해소 시 status=done(INVARIANT #3).** 한 폴링 cycle에서 escalate되어야 할 dedup_key 집합(active set)을 계산하고, **성공적으로 fetch한 repo** 범위 안에서 active set에 없는 기존 github_pr 신호를 `status=done`으로 전이(매트릭스에서 소멸). CI green(PR은 open이나 reason 사라짐) / merged·closed(open 목록에서 사라짐) 둘 다 커버. fetch 실패한 repo의 신호는 fresh 데이터가 없으므로 auto-resolve 대상에서 제외(오탐 방지).
- **폴링 = 주기 폴링 + backoff(사용자 결정, INVARIANT #5 bounded).** 프런트 PR Radar 뷰가 TanStack Query `refetchInterval`(약 3분)로 주기 폴링하고, 실패 시 bounded `retry`(지수 backoff)로 후퇴 — 무한 tight loop 아님. 한 cycle 내부에서도 octocrab 호출은 `github.rs`의 bounded `with_retry`(시도 캡 + 지수 backoff + jitter, terminal 재시도 안 함)를 거친다. 항상-on 백그라운드 Rust 폴링 태스크는 도입하지 않음(뷰 마운트 동안만 폴링; 라이프사이클/킬스위치 복잡도 회피, Phase 4 범위 최소화) — 필요 시 추후.
- **테스트 가능 seam = `PrProvider` 트레잇(notion.rs `NotionWriter` 패턴 재사용).** GitHub 호출(octocrab)은 `HttpPrProvider`에 격리하고, radar 코어(버킷 분류·escalate·dedup·auto-resolve)는 `PrProvider` 트레잇 + 실 DB로 fake provider로 검증(헤드리스 CI 가능). 실 GitHub fetch·CI/conflict 도출·실네트워크는 사용자 관찰 항목(Phase 2 octocrab ping과 동일).
- **github.rs는 자체 `GithubError`+bounded retry(notion.rs와 비공유, 의도적).** GitHub은 rate limit(~5000/h + secondary)·`Retry-After`·`X-RateLimit-Reset` 등 Notion과 다른 재시도 관심사를 가져 모듈별로 에러 분류/재시도를 소유한다. notion.rs를 건드리지 않아 Phase 3 무회귀(한 PR=한 관심사, broad refactor 금지 규칙 부합). 공통 retry 추출은 향후 정리 후보.
- **readiness 버킷(우선순위) = Merged Cleanup > CI Blocked(CI 실패 또는 conflict) > Stale(open·{N}일 무활동) > Needs Self Check(draft 또는 미self-check) > Ready.** open PR은 per-PR check-runs로 CI 도출 + `mergeable_state==dirty`로 conflict. Merged Cleanup은 state=closed 최근 페이지 1장에서 `merged_at` 최근분만(per-PR CI 호출 없음, bounded). 5버킷 모두 의미있게 채움.
- **수동 self-check = 로컬 상태(마이그레이션 0004 `pr_self_checks`).** `(repo_full_name, pr_number)` UNIQUE 행 존재=self-checked(routine_checks 패턴). GitHub 상태 아님(로컬 결정). `set_pr_self_check`로 토글, radar 도출이 조인.
- **신규 의존성: `regex`(ticketKeyPattern 매칭) + `chrono`(age/stale 날짜연산, octocrab가 이미 transitive로 사용).** PR number 등은 specta export 위해 u32로 변환(i64/u64 export 금지 가드). 새 Tauri 권한 불요(octocrab=Rust, PR URL 열기는 기존 opener `openExternal` 재사용).
- **auto-resolve는 사람이 분류한 카드도 done 처리(의도, reviewer 지적).** escalate된 PR 신호를 사람이 Q1으로 드래그한 뒤 CI가 green이 되면 auto-resolve가 `status=done`으로 바꿔 매트릭스에서 사라진다. INVARIANT #1 위반 아님(`quadrant`는 보존되고 `status`만 바뀜 — 시스템 파생 ambient 신호의 *존재 이유*가 사라진 것)이고 INVARIANT #3("원인 해소 시 신호 소멸")에 부합. 사람의 분류 *행위*보다 원인 해소를 우선해 가시성을 정리하는 것이 의도된 동작. (필요 시 추후 "사람이 만진 PR 신호는 done 대신 보관 표시" 옵션 검토.)

## Phase 5 — Worktree & Branch Diff Viewer (read-only) (2026-05-21)

- **git 접근 = `git` CLI 셸아웃(사용자 결정).** architecture §8은 "git2(libgit2) 우선, 복잡 케이스 CLI"로 적었으나, Phase 5는 **read-only diff 뷰어**라 (1) 프런트 구문강조용 raw unified diff *텍스트*가 필요(git2는 구조화 hunk를 텍스트로 재직렬화해야 함), (2) 3-dot merge-base(`base...head`)·numstat·porcelain v2 status·`rev-list --left-right --count`가 CLI에서 정확/단순, (3) git은 이 앱의 하드 전제(worktree/PR 도구)라 CLI 의존이 합당, (4) Phase 7 Codex도 어차피 `tokio::process` 사용 → CLI 인프라 공유. 새 C 의존성(libgit2) 회피. **git2-우선 문서 권고를 의도적으로 벗어남**(이 use case 한정). git.rs는 read 서브커맨드만 호출(worktree list / status / for-each-ref / diff / rev-list) — checkout/reset/commit 등 mutating 커맨드 없음(INVARIANT #6 read-only).
- **영속 없음 = ambient 도출(PR Radar 선례, 사용자 결정).** `Worktree`/`DiffFileSummary`/`DiffMode`/`FileChange`/`WorktreeStatus`는 IPC DTO(models.rs)로만 정의하고 **신규 마이그레이션 없음**(PR Radar처럼 매 호출 fresh 도출). git 호출은 로컬·빠르고 네트워크 없음 → 캐시/스냅샷 불필요. architecture §4의 `Worktree`/`DiffFileSummary`는 DB 테이블이 아니라 IPC 반환 타입으로 해석. "가장 작은 변경"(AGENTS.md) 부합.
- **bound = 서브프로세스 timeout(INVARIANT #5 해석).** 로컬 git은 결정적이라 재시도가 무의미 → backoff/jitter 재시도 루프 없음. 대신 각 `git` 호출을 `tokio::time::timeout`(20s)으로 bound하고 실패는 terminal로 노출(삼키지 않음). "무한 retry/poll 금지"의 핵심(무한 루프 없음)을 충족. github.rs `with_retry`(원격·rate limit)와 달리 모듈 분리.
- **테스트 가능 seam = `GitProvider` 트레잇(PrProvider 패턴 재사용).** 실제 git 셸아웃은 `CliGitProvider`에 격리, 코어(`collect_worktrees`: 멀티레포·projectId 필터·repo별 실패 격리·status→enum 요약)는 트레잇 + fake provider로 검증. **파싱은 순수 함수로 단위 테스트**(`parse_worktree_list` porcelain, `parse_status_v2` ahead/behind/dirty, `parse_numstat`, `parse_name_status`, `diff_range_args` 4모드, `summarize_status` 우선순위). 실제 git 실행·실 diff 렌더는 git이 테스트 셸 PATH에 없을 수 있어(HANDOFF 운영노트) cargo test 제외 → 사용자 관찰 항목(`pnpm tauri dev`, PR Radar 실네트워크와 동일).
- **비교 모드 4종 → git 인자.** `working`=`git diff`(워킹트리 vs index, 미커밋 unstaged) / `staged`=`git diff --cached`(index vs HEAD) / `vs_base`=`git diff <base>...<head>`(3-dot, head 기본 HEAD) / `branch↔branch`=`git diff <base> <head>`(두 ref 직접 비교). ref가 `-`로 시작하면 거부(arg injection 가드), 파일 경로는 `--` 뒤로 전달.
- **대용량 diff 비차단 = 파일목록 먼저 + 파일별 지연 로드.** `worktree_diff_files`(numstat+name-status 머지)로 파일 목록만 먼저 받고, 선택한 파일만 `worktree_file_diff`로 hunk 텍스트 lazy fetch(TanStack Query `enabled`). 폴링 없음(로컬·on-demand; PR Radar의 refetchInterval 불요) — 뷰 진입+수동 새로고침만. 구문강조는 **diff-line 강조**(추가/삭제/hunk 헤더 CSS)로 — 언어 문법 하이라이터(heavy dep) 도입 안 함(추후); "가장 작은 변경".
- **diff 상태 = M/A/D/R(architecture DTO 정합).** `FileChange`는 serde per-variant rename으로 `"M"/"A"/"D"/"R"` 직렬화(architecture.md `DiffFileSummary` 문구와 동일 TS union). rename은 name-status `R###`에서 new 경로, numstat은 `-`(binary)를 0으로. `WorktreeStatus` 요약 우선순위 = Diverged(ahead&behind) > Dirty > Ahead > Behind > Clean (ahead/behind 수치는 별도 필드로도 노출 → 배지). specta i64/u64 export 금지 → ahead/behind/adds/dels = u32.

## Phase 6 — status mismatch 감지 (Notion↔PR drift) (2026-05-21)

- **drift 방향 = PR merged + Notion≠done 단일 케이스(사용자 결정, 정본).** done-criteria가 명시한 "Notion Doing + PR Merged" 케이스만 mismatch로 본다(역방향·stale 등은 미도입 — over-engineer 회피). PR이 머지됐는데(=GitHub 사실) 연결 백로그 상태가 done 목록에 없으면 drift. 사용자 코멘트("노션-깃헙 연결돼 자동")는 *조인은 이미 연결됨*으로 해석하되, **상태 동기화는 사람이 누락**할 수 있어 그 누락을 잡는 것이 Phase 6의 가치. 양방향/넓은 임계는 필요 시 추후.
- **done 판정 = 프로젝트별 done 상태 이름 목록(사용자 결정).** `projects.notion_done_statuses`(마이그레이션 0005, JSON 배열 문자열)에 done으로 볼 상태 이름들을 사용자가 설정(`set_notion_done_statuses` IPC + ProjectCard 편집기). 비교는 trim + `eq_ignore_ascii_case`(ASCII 케이스 폴딩; 한글 등 비ASCII는 정확매칭 — done 라벨은 사용자 지정 정확명이라 무해). **목록 비면 mismatch 감지 비활성**(noise 0) — 미설정 프로젝트는 신호를 만들지 않는다. Notion `status` 타입의 "Complete" 그룹 자동판정(스키마 read)은 select 타입 미지원이라 채택 안 함 — 사용자 명시 목록이 select/status 모두 커버하고 단순.
- **Notion 상태 read 범위 = backlog DB 전체 query(사용자 결정).** Phase 3는 write만 했고 read 미러가 없어, mismatch 비교용으로 `NotionReader` 트레잇 + `HttpNotionReader`(notion.rs) 신설 — `POST /v1/databases/{id}/query`(read)로 백로그 페이지를 bounded 페이지네이션(`MAX_QUERY_PAGES=10` × 100 = 1000건 상한)으로 받아 페이지마다 title(plain_text 연결)·status(status 타입 우선, 없으면 select) 추출. 스키마 가정 최소화(속성명/언어 무관, type 기준). **POST지만 mutation 아님**(query=read) → INVARIANT #2/#7(Notion=내용 SSOT, 상태는 read만) 준수.
